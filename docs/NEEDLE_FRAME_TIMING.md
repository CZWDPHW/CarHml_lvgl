# 指针流畅度与 60 FPS 调度（2026-11-19）

已确认：板端 LVGL 显示与动画周期为 20ms，主程序快照采样也为 20ms，调度目标约 50fps。
本次改为 16ms（整数毫秒下理论约 62.5 次/秒），采样和主循环最大休眠跟随同一个周期，为约 60fps 留出调度空间。16ms 是调度参数，不代表硬件扫描与 LVGL 已经同步，也不证明稳定 60fps。

指针已有 100ms 线性插值，相同目标不会重启动画，新目标从最近显示角度接续。此次保留角度公式及插值时长；新增每 16ms 前进、重复快照不重启、到达目标的回归。MCU 更新间隔大于 100ms 时，指针可能先到目标再等待下帧；没有实际收帧间隔前，不增加预测车速或延长动画带来的跟随延迟。

板端 `perf:` 日志每 2 秒输出：

- `fps`：LVGL 完成绘制的次数/秒，静止画面无需持续重绘，不能用静止时的低值判断性能。
- `render_avg` / `render_max`：一次绘制耗时，包含同步 framebuffer 提交。
- `slow_render`：本窗口绘制超过 16667us 的次数；持续存在时单帧绘制已超过 60fps 预算。
- `frame_gap_max`：相邻 RENDER_START 的最大间隔，包含静止等待和 MCU 数据间隔，只有持续运动时才适合用于观察顿挫。
- `handler_hz`：事件循环调用次数，不能当成显示 FPS。

在实际指针持续变化场景，记录连续数行日志再判断 CPU 绘制、偶发长帧与数据节奏。当前使用软件绘制和 mmap framebuffer，同步写入不等于 VSync 双缓冲；CPU 能画到 60fps 也不保证显示无撕裂。是否需要更换显示后端或调整缓存，应以板端帧耗时和显示驱动能力为依据。

使用 Release 交叉编译并替换程序后才生效。此提交没有承诺实机 60fps，没有改变 framebuffer 缓冲数量，也没有在本机改动车辆数据。

本地验证：指针回归 205 项检查零失败，Windows 无窗口 UI 回归 9/9 通过；BOARD 主程序通过声明/语法检查，尚未进行本轮 Linux 交叉链接或实机帧率测量。
